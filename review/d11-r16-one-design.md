# D11 r16 — 하나의 설계 (r15 선택지 프레임 폐기)

> 경위: 유저 회신 (2026-08-12, Q1–Q4). 요지 세 가지가 프레임을 교체했다:
> ① **Q1 재조준** — idle wake ~10s는 충분하다. 진짜 문제는 **active하게 일하는 세션에의
>   개입**이다. native 메시징은 거의 즉각 컨텍스트에 개입하는 걸로 보이는데, 자율 우편함
>   확인이나 stop hook에 기대면 장기 자율작업 중인 세션은 수십 분 뒤에야 확인할 수 있다.
> ② **fallback 타워 지양** — "다단계 fallback을 통해 안전하게 동작하는 거대하고 복잡한
>   설계"보다 "하나의 단순하고도 아름다운 이상적인 설계". 헌법 문면(R7 등)은 도그마가
>   아니라 취향의 명문화다.
> ③ **설계의 단순함 ≠ 구현의 원시성** — 필요하면 현대적 구현을 써도 된다. 중요한 건
>   설계의 아름다움이다.

## 1. 화두에서 다시 — 진짜 칼라라면 어떻게 동작해야 하나

원전의 칼라는 편지 보관소가 아니다. **항상 접속돼 있는 교감의 매질**이고, 프로토스는
그 안에 "들어가" 있다. 시스템으로 번역하면:

> **모든 노드의 우편함은 하나의 트리의 사본이다. 신경이 살아 있는 동안 사본들은
> 초 단위로 수렴하고, 신경이 죽어도 트리는 디스크 위의 진실로 남는다.**

이 한 문장이 설계 전부다. "live 층 / watch 층 / mailbox 층"은 없다 — **복제 설계
하나**가 있고, 링크가 있으면 수렴이 즉시이고 없으면 다음 펌프까지 기다릴 뿐이다.
폴백은 별도 층이 아니라 같은 설계의 저하 모드다.

## 2. 세 기관

| 기관 | 실체 | 역할 | 상태 |
|---|---|---|---|
| **뇌** | `bin/khala` (bash, 기존) | 의미론 전부 — send 안착, 배달, ack 정산, dedup, bounce, 위생. 멱등 로컬 연산 + 수동 펌프(sync) | 불변 (D12 수리만) |
| **신경** | `khala link` (신규, Go 동봉 바이너리) | 의미론 0의 파일 이벤트 펌프 — 스풀·presence 트리의 변화를 상대에게 즉시 밀고, 받은 파일을 원자적으로 놓고, 도착 시 로컬 뇌(`khala sync`)를 찌른다. 내용을 이해하지 않는다 | v0.2 신규 |
| **귀** | `khala watch` (기존 개량) | 세션이 arm한 로컬 감시자 — inbox/new에 파일이 생기면 종료 → 하니스 task-notification → 세션 컨텍스트 주입 | 로컬화 개량 |

분리의 요점: **의미론의 구현이 두 벌로 갈라지지 않는다.** 신경은 파일을 나를 뿐이라
at-least-once·멱등 dedup·e2e ack·bounce가 전부 뇌의 기존 코드 그대로다. 신경이
언제 죽어도 해는 지연뿐 — 칼라의 상태는 전부 프로세스 밖 디스크(스톱갭 한계 ④ 면역
불변).

구현 자유의 사용처 (유저 ③): 신경만 Go — fsnotify(mac 포함 크로스플랫폼 파일
이벤트), 지속 연결, 지터 재접속이 bash 3.2 밖의 요구라서다. GOOS/GOARCH 정적
크로스빌드로 6플랫폼 부담 재평가 통과, 배포는 bin/khala와 같은 scp. gRPC·새 프레임워크
불요 — 프로토콜은 stdio 위 자체 프레이밍 하나다(아래).

## 3. 캐리어 — 프로토콜은 파이프 위, ssh는 프로덕션 파이프

`khala link`는 **임의의 바이트 파이프 위에서 동작한다**: 프로덕션 캐리어 =
`ssh <hub> khala link --serve` (기존 키·ssh config·지형 통과 전부 상속 — 새 포트 0,
새 인증 0, 영원히). 테스트 캐리어 = serve 직접 exec (같은 프로토콜, 캐리어만 명시적
교체 — silent fallback 아님). cloudflare tunnel이 생기면 ssh가 그 위를 타므로 신경은
무변경.

수신측 쓰기 규율: 전송 완료 후 tmp→rename (뇌의 원자성 규율 그대로). 링크가
전송 중간에 죽어도 스풀에 찢어진 파일이 생기지 않는다 — 잔해는 tmp에만.

## 4. 토폴로지 — 허브 중계만으로, 오늘 지형에서, 전 함대 실시간

- 각 스포크 노드가 **노드당 하나의 상시 링크**를 허브(b200)로 다이얼한다. 허브에서
  도는 것은 sshd의 자식(serve)들뿐 — **허브 상주 데몬 0 유지**. serve들끼리의 조정은
  허브 파일시스템 이벤트로 한다: **허브에서도 파일시스템이 버스다.**
- A→B 흐름: A의 send 안착 → A링크가 허브 스풀에 즉시 push → B담당 serve가 파일
  이벤트로 감지 → B링크로 즉시 push down → B의 뇌가 배달 → B의 귀가 알림.
  **오늘 지형(모두→b200 가능)에서 터널 없이 함대 전체 초 단위** — 이게 r16의 발견이다.
- 직결 엣지(터널이 열든, 같은 tailnet이든)는 링크가 허브 대신/추가로 피어를 다이얼하는
  것 — 같은 프로토콜, config 한 줄, 설계 불변. r15의 "L2"는 독립 선택지가 아니라
  토폴로지의 자연 확장으로 소멸.
- config 델타 0: 링크는 기존 `mailbox`/`peer` 선언을 그대로 쓴다 (R12).
- 재접속: 지터 있는 백오프 (V2 실측 상속 — MaxStartups herd 영구 회피).
- 링크의 수명 모델: 노드 단위 싱글턴(락파일), 세션과 독립(의도적 detach — 세션들은
  훅에서 ensure-start만). 세션당 watch N개가 원격 펌프를 각자 돌리던 현행보다 상주가
  오히려 줄어든다: 원격 연결은 노드당 1개로 수렴하고, 귀들은 로컬 폴로 내려온다.

## 5. active 세션 개입 (Q1의 진짜 질문)

주입 지점의 사실관계부터: **native 메시징도 "즉각"이 아니라 다음 툴 라운드 경계에서
드레인된다** (스킬 문면·실측 일치). active 세션은 툴 라운드가 잦아서 즉각처럼 보이는
것. 그리고 khala의 wake 경로(백그라운드 태스크 종료 → task-notification)도 **정확히
같은 경계에 주입된다** — 오늘 이 세션이 산 증거다: eddy의 편지들이 작업 한중간에
task-notification으로 꽂혔고, 자발적 우편함 확인은 0회였다.

그러므로 active 세션 지연 = fabric 초 단위(§4) + max(진행 중 툴콜의 잔여, 0) —
**native와 같은 급이고, 같은 천장을 공유한다.** 진행 중인 단일 툴콜의 한중간은
native도 못 끊는다. 그 천장을 넘는 유일한 레인은 유저 입력 레인인데, 그것은 유저의
신원이다 — R13이 금지하고, 칼라는 영원히 쓰지 않는다.

남는 진짜 위험은 유저 지적 그대로 "**귀가 안 서 있는 구간**"이다 (watch는 1회성이라
발화 후 재무장 필요 — 지금은 세션의 규율에 의존). 규율을 구조로 바꾸는 것이 D9 훅
3종이다:

1. **SessionStart**: inbox 드레인(상한) + 귀 arm + 링크 ensure-start.
2. **드레인 직후 재-arm** (wake 처리 스킬 문면): 깨어난 턴이 귀를 다시 세우고 시작.
3. **Stop 훅**: 턴이 끝날 때 귀가 없으면 세운다 — "idle이면 반드시 armed" 불변량.
   (Stop 훅은 확인 시점이 아니라 무장 수리 장치다 — 확인은 상시 귀가 한다.)

세 훅이 있으면 "수십 분 무확인" 경로는 구조적으로 닫힌다: 턴 중 도착은 경계에서
주입되고, 턴 사이 도착은 armed 귀가 깨운다.

## 6. presence 통합 + D12 (Q4 확정)

- heartbeat/watching 파일도 트리의 파일일 뿐이므로 **같은 신경으로 실시간 복제된다**
  — 별도 gossip 프로토콜이 설계에서 소멸. 링크가 살아 있는 노드의 presence는 함대
  전체에서 초 단위로 신선하다.
- **D12 (유저 위임 하 ink 확정)**: heartbeat는 발화(send/inbox)만 갱신 — watch는
  시작 1회 갱신도 제거 (orphan watch의 산 자 행세 차단, eddy 선견해 합치). watching
  (귀 열림)은 별도 파일: arm 시 생성, 정상 종료 시 삭제(trap), 잔해는 TTL 소독.
  presence 표에 watching 열 추가 — "asleep+watching = 편지를 넣으면 깬다"가 정직하게
  보인다. 라우팅은 여전히 presence 무의존(표시 전용 — 발견 실패가 배달 실패로 못
  번진다).

## 7. 헌법 정비 (r16)

- **R7 정제**: "제3자 서버 없음" → "제3자는 암호화된 바이트만 나르고(내용 열람 불가)
  상태를 갖지 않으며, 없어도 칼라는 성립한다." 근거: 현행도 DERP(제3자 중계)를 실사용
  중이라 원문면과 충돌. 이 문면 하에서 cloudflare tunnel은 DERP와 같은 급 — 개설은
  유저 재량·비차단 (유저: 원칙은 취향의 명문화지 도그마 아님).
- **D4 진화**: "상주 데몬 기본 없음"에 신경이 노드당 1개 옵트인 상주로 추가. 허브
  쪽은 여전히 상주 0(sshd 자식뿐). 링크 없이도 칼라는 완전 동작(저하 모드) — 옵트인
  원칙 유지.
- **§9.2 언어 규칙**: 뇌 bash 불변("모든 온디스크 포맷은 grep로 읽힌다" — 신경은
  포맷을 만들지 않으므로 무관), 신경만 Go. 전환 기준(6플랫폼 크로스빌드 부담)은
  정적 빌드로 통과 + 유저의 구현 원시성 해제.

## 8. 구현 계획 — 수용 속성 사전 등록

**lane A (bash, 소규모): D12 수리** — watch heartbeat 제거 + watching 파일 + presence
열 + TTL. 기존 스위트의 해당 속성 수정 포함.

**lane B (Go): `khala link` v0** — 속성:

1. **전파 지연**: 링크 확립 상태에서 A send 안착 → B `inbox/new` 등장 ≤ 2s (stdio
   캐리어 테스트 rig).
2. **양방향**: 같은 링크 위 B→A 역방향도 ≤ 2s (재수립 없이).
3. **허브 중계**: A→hub→B 3홈 rig에서 B가 A를 다이얼한 적 없이 ≤ 3s.
4. **저하 모드**: 링크 kill 후 send → 유실 0, 수동 `khala sync`가 배달; 링크 재기동
   시 잔여분 자동 수렴.
5. **원자성**: 전송 한중간 kill이 스풀에 찢어진 파일을 남기지 않는다 (잔해는 tmp에만).
6. **의미론 무접촉**: 기존 4 스위트 무변 통과 + 같은 편지 이중 전파 시 재배달 0
   (dedup·ack 재생성이 링크 경유에서도 문자 그대로).
7. **재접속 지터**: 단절 시 지터 백오프 재수립 (로그 증거).
8. **싱글턴**: 노드당 1 링크 — 중복 기동은 즉시 정상 종료 + 안내.
9. **무리스너**: serve는 stdio 전용 — 포트 바인딩 0 (listening socket 부재 증명).

**귀 개량** (lane A 또는 B에 흡수): 링크 신선 마커가 살아 있으면 watch는 원격 펌프
생략, 로컬 1s 폴 — 마커가 삭으면 현행 interval sync로 자동 복귀.

**V3 결과 (eddy, mbp 자연 수면 사이클, 2026-08-13 — 강제 개입 없는 관찰)**:
~09:56 뚜껑 닫힘 → 09:56:51 허브 serve가 설계 타임아웃 문면 그대로 사망("no
inbound protocol frame for 1m0s") → 수면 중 발송분은 spool/for/mbp 적체(정상
저하 모드) → 10:09:07 재다이얼·HAVE 교환 재수립 → 수 초 내 spool 드레인 완주.
**핵심 발견 — DarkWake 배달**: 재수립 시점의 mbp는 ssh 불가( = full wake 아님).
macOS 유지보수 깨어남(DarkWake, TCPKeepAlive=active) 중에 dial 백오프가 물려
배달까지 완주한 것 — **잠든 mac도 뚜껑을 안 열어도 DarkWake 주기(전원 연결 시
수 분~수십 분)마다 편지를 받는다**. 배달 지연 상한 = DarkWake 주기. 보너스:
8초 강제 수면에선 TCP가 안 끊기고 같은 프로세스 그대로 재개 — 짧은 수면은
