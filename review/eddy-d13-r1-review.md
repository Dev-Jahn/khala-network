# eddy 리뷰 — D13 r1 (communion streams), 2026-08-13

평결: **합의 — 레인 발사 가능.** mail/stream 의미론 분리, 발행자 샤드 구조,
나이 수렴 삭제, §5b presence 접합 전부 견고하다. 아래는 요청받은 세 지점의
검증 결과와, 브리프에 반영을 권하는 발견 셋(F1–F3).

## 1. §8 — 허브 transit 삭제 비적용, serve 코드와 충돌 없는가

**충돌 없음, 코드로 확증.** transit 삭제는 class 전역 스위치가 아니라
후보(candidate)별 옵트인 플래그다:

- `link/watch.go:261,326` — `deleteAfterStored: t.role == "serve"`는 **class
  "spool" 후보에만** 설정된다.
- `link/watch.go:281,319` — presence 후보는 이 플래그 자체가 없다.
- `link/pump.go:434-443` — 삭제는 `c.deleteAfterStored`가 참일 때만, 386의
  재출현 정리도 같은 플래그 뒤에 있다.

즉 class "stream"을 presence처럼 플래그 없이 추가하면 serve는 STORED 후에도
파일을 건드리지 않는다 — 설계가 원하는 "허브도 투영 소유자" 그대로. dial 쪽
가드(`pump.go:435-436` "dial reached transit unlink" 내부 오류)와도 정합.

문구 하나만: §7 "자기 샤드 제외 전 샤드"의 '자기'가 **수신 스포크**임을 레인
브리프에 명시할 것 (presence 코드의 echo 방지 규칙과 동일하다는 뜻인데, 문면만
읽으면 허브 자신의 샤드로 오독 가능 — 허브 샤드는 당연히 fan-out 대상이다.
b200 세션 넷이 commons의 주 발화자가 될 테니 오독하면 스트림이 안 흐른다).

## 2. §5 — 부활 불가 논증의 구멍

**진짜 부활 경로는 못 찾았다.** push 자기-샤드 한정 + prune-후-push 순서 +
허브 동일 규칙의 세 다리는 서로 독립적으로 성립하고, 셋 다 무너져야 부활이
생긴다. 다만 가장자리 둘:

- **(무해) 경계 플랩**: 시계가 빠른 노드는 항목을 먼저 지우고, 허브가 아직
  갖고 있으면 pull이 도로 설치하고, 다시 지운다 — 허브가 만료할 때까지 반복.
  창은 시계 오차만큼(수 분), 비용은 항목당 재복사 몇 회. 논증을 깨지 않는다.
  reconcile 로그에 한 줄 남기면 관찰 가능해서 족하다.
- **F1 (반영 권고) — 위조 '미래' 항목은 준불멸**: 수명이 id의 epoch에서
  나오므로, 시계가 크게 미래인 노드(또는 버그)가 만든 항목은 `epoch+retain`까지
  전 함대에서 안 죽는다. 2040년 시계면 14년짜리 항목이다. 수용 속성 6이 "위조
  노후"의 소멸만 다루는데 **거울상이 빠져 있다**. 권고: say 시점(뇌가 epoch을
  직접 찍으니 로컬 시계 신뢰)은 그대로 두되, **설치/드레인 측에 미래 한계
  가드**(예: `epoch > now + 1d` → quarantine — 기존 digest quarantine과 같은
  기계)를 넣고, 속성 6′로 사전 등록: "위조 미래 항목은 설치 거부/격리되고 전파
  0". presence heartbeat는 상시 덮어써져 이 문제가 없지만 스트림 항목은
  불변이라 박제된다 — 스트림에서 처음 생기는 위험이다.

## 3. commons 자동 합류 — 소음 시나리오

드레인 쪽 방어(커서=합류 시점부터, mail 우선, 예산 공유, 초과 요약)는 충분하다.
자동 합류가 1회용 CLI 발신에는 적용 안 되는 것(join은 SessionStart 훅 산물)도
확인. 남는 소음원은 하나이고, 그것이 이 설계의 심장과 같은 기계다:

- **F2 (반영 권고) — wake 증폭**: "say → 상대 wake 초 단위"는 교감의 체감이자
  소음의 공식이다. commons에 한 마디 = **함대의 armed watch 전부가 깬다** =
  세션 수 × 발화 수만큼 모델 턴이 태워진다. 지금 armed 6~8 세션이면 시간당
  say 몇 건에도 유의미한 토큰 비용이다. 사회적 규율("commons엔 중요한 것만")로
  버틸 수 있는 규모지만, 나중에 고치려면 watch 의미론을 다시 여는 대공사가
  된다. 권고: join 상태에 넷째 값 하나 — `joined <epoch> quiet` — 를 v1에
  넣어라. quiet 스트림은 **드레인엔 포함되되 watch를 깨우지 않는다** (다음
  자연 깨어남에 실려온다). commons 기본값은 loud 유지 — 교감의 체감은 기본으로
  지키되, 수다스러운 스트림에서 개별 세션이 귀만 닫을 자유를 준다. 비용은
  watch 종료 조건에서 조건 하나, 상태 파일 문법 한 단어다.

## 4. F3 — join/cursor에 같은 축적 문제가 재생산된다

§5b가 presence의 축적을 고쳤는데, **이 설계가 새로 만드는 로컬 상태(join/,
cursor/)에는 수명이 없다.** 은퇴·개명한 세션 이름(jahn→clawd 같은)의
join/cursor 파일이 영원히 남는다 — 오늘 청소의 원인이 된 것과 같은 계급의
공백을 새 파일 가족으로 재발명하는 셈이다. 로컬 전용이라 전파 문제는 없으니
수리도 로컬로 족하다. 권고: reconcile (c)에 한 규칙 — **그 세션 명의의
presence가 retired이거나 나이 GC로 소멸했으면 join/cursor도 걷는다** (산
세션의 오랜 침묵과 구별하려면 presence 연동이 나이 단독보다 안전하다 — 30일
조용했던 산 세션의 커서를 지우면 무재배달 보장이 깨진다). 속성 13에 한 절
추가로 사전 등록 가능.

## 5. 그 밖에 확인한 것 (발견 없음)

- (epoch,id) 병합: id 문자열이 전 노드 동일하므로 정렬 결정성 성립.
- mail 우선 드레인: 의무 기아 없음, 스트림 기아는 요약+커서 연속성으로 정직.
- C1(경로당 작성자 1): 샤드 구조가 presence와 동형 — 쓰기 경합 0 주장 타당.
- C3 적용 범위(no-clobber+quarantine만): 항목 불변이므로 옳다.
- NOT-in-v1 목록: 전부 동의. 특히 reply-all 부재는 §1의 논리적 귀결.

## 6. 게이트

r17 전례대로: **F1·F2·F3를 브리프에 접합하는 조건으로 합의.** 셋 다 설계의
뼈대를 건드리지 않는 국소 증보다(가드 하나, 상태값 하나, GC 규칙 하나).
접합 후 lane A 발사에 이의 없음. lane B는 A 머지 후 — §7의 min(minor) 협상과
저하 모드 원칙도 그대로 좋다.
