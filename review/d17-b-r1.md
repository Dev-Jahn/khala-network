1. **게이트웨이는 독립 노드 `gateway`다** (ChatGPT 브리지가 mini 위에 `chatgpt` 노드로 뜬 방식 그대로): 자기 `KHALA_HOME`
   (`~/.local/share/khala-gateway/node`, `self gateway`, `peer mini` loopback, `mailbox mini`), 자기 중계 데몬, 자기 gateway 데몬.
   호스트는 mini지만 주소는 `user@gateway`로 고유하다. 나중에 Discord 등을 더해도 노드 하나에 어댑터를 얹는다.
2. **새 메시지 타입을 만들지 않는다.** 사용자 메시지는 `Type: message`로 보내고, **발신자 이름 `user`를 예약**해 식별한다:
   `From: user@<node>`면 사용자 메시지다. `user`는 `reserved_name`/Go `isReservedIdentity`/채널 `RESERVED_IDENTITIES`에 들어가
   어느 노드에서도 세션이 그 이름을 가질 수 없고, **`gateway.conf`가 있는 노드에서만** `khala send --as user`와 `user` 신원의
   `inbox list/read/ack-read`가 허용된다. r1 §2.2의 `Origin`/`Origin-Ref` 헤더, §2.4의 `gateway-enqueue`·토큰 파일, §2.5 형식 검사는
   **전부 폐기**. 회신 스레딩용 매핑(메시지 Id ↔ Telegram chat/thread/message id)은 게이트웨이의 자기 상태 파일에 둔다
   (Id는 게이트웨이가 만들었으므로 안다). 중복 방지는 기존 `send --request-id tg-<update_id>` 원장으로.
   결과: 구버전 노드도 그대로 배달하고 보통 메시지로 보여 준다(롤 순서 제약 없음). 위조 한계는 r1과 같다(같은 uid).
3. **회신 주소는 `user@gateway` 하나**. `khala-gateway` 예약 이름은 DESIGN §3.4에서 "예약만, 수신 불가"로 정리한다. 혼선 점검:
   현재 클러스터에 `khala-gateway`를 owner로 둔 watchdog는 없고(09-22 실측 presence), 이 이름으로 등록된 세션도 없다.
4. **긴 답장**: Telegram `sendMessage`의 4096자는 API 상한이라 바꿀 수 없다. 대신 (i) 4096자까지는 그대로, (ii) 그 이상은
   UTF-16 단위로 안전하게 분할해 최대 3개까지 연속 전송, (iii) 3개를 넘는 길이(≈12k자 이상)면 본문 전체를 `.md` 파일로
   `sendDocument`(50 MB 상한)하고 첫 300자를 캡션으로 붙인다. 임계는 `gateway.conf`의 `telegram chunk-limit 3`으로 조정.
5. **상태어**(토픽 자동 게시 3종): `connected`(세션이 클러스터에 등록됨) / `stalled: unread for N min`(등록은 살아 있으나 알림을
   15분째 처리 못 함) / `disconnected`(등록 사라짐). 한국어 UI 없음 — Telegram 게시는 영어 표준어.
6. 만료 기본 3일(`gateway.conf` `user expires 259200`), 미처리 경보 15분(`stall-after 900`).
7. 레인 재편: **B-GW**(새 파일만: `link/gateway*.go`, `link/telegram*.go`, 가짜 어댑터, `test/gateway.sh`, main.go 1줄)를 먼저 띄운다.
   **B-CLI**(`user` 예약·게이트웨이 노드 예외·inbox read `=== user` 블록·SKILL)와 **B-CONDUIT**(`user:` 프레임 줄·항상 next·`USER ·` 표시)은
   용어 정리 레인(같은 파일들을 손댐)이 병합된 뒤 띄운다.

## 0. 요약

- 코어에 새로 들어가는 것은 네 가지뿐이다. 헤더 `Type: user`, 예약 이름 `user`, 수신함 읽기의 `=== user (N) ===` 블록,
  수신 알림 프레임의 `user: N` 줄. Telegram은 `khala-link gateway` 안의 어댑터 하나이며, `gateway.conf`가 있는 노드에서만 뜬다.
- 게이트웨이는 헤더를 직접 쓰지 않는다. 헤더를 쓰는 곳은 지금처럼 `bin/khala` 하나로 두고, 게이트웨이 전용 내부
  하위 명령을 토큰으로 막아 둔다(§2.4). 멱등성은 이미 있는 `--request-id` 원장이 맡는다. 키가 `tg-<update_id>`라서
  Telegram offset 관리와 중복 제거가 한 장치로 끝난다.
- 세션이 사용자에게 답하는 쪽은 평범한 메시지(`khala send user@mini --reply-to <Id>`)다. 게이트웨이는 기존 pull-only
  API(`inbox list/read/ack-read`)로 자기 수신함을 읽으므로, 파괴적 수신함 읽기가 게시 전 유일한 사본이 되는 일이 없다.
- 대시보드는 지금처럼 별도(`khala-link dashboard`)로 둔다(§4.8).
- `go-telegram/bot` v1.27.0은 받아지고 정적 빌드도 되지만 **쓰지 않기를 권한다**. 이 라이브러리의 폴링 루프는 핸들러가
  끝나기 전에 offset을 전진시킨다(§4.3). Bot API 호출 8개를 stdlib로 직접 부른다. 새 의존성이 없다.

## 2. 헤더 `Type: user`

### 2.1 이름: `user` 대 `operator`

GPT-Pro는 `Type: operator` + Ed25519 서명을 권했다(review/gpt-pro-d17-review.md B2-B3). DESIGN §9.6 3.5는 그 자리로
`operator`를 예약해 두었다(DESIGN.md:787-799). 이 브리프는 서명 없는 `Type: user`를 지정한다. 이 문서는 브리프대로
`user`를 스펙으로 삼되, 두 안의 차이를 기록하고 최종 선택은 열린 결정 1로 넘긴다.

- `user`(v1, 서명 없음): 출처 보증은 "CLI는 토큰 게이트 없이 `user` 봉투를 만들지 않는다"와 수신함 읽기의 형식 검사(§2.5)까지다.
  같은 uid 프로세스가 파일을 손으로 만들면 위조할 수 있다. DESIGN §5.6 "전부 유저 본인 머신" 위협 모델 안에서 받아들이는 한계다.
  `operator`와 `Auth: unverified` 경로는 나중의 서명 레인을 위해 그대로 남긴다.
- `operator`(서명): 코어 파서와 배달이 이미 준비돼 있어서 **혼재 클러스터에서도 구 노드가 배달한다**(bin/khala:2896). 대신
  서명·키 배포·재생 방지를 구현해야 하고, 서명이 없으면 구 노드의 SKILL이 "보통 편지"로 취급한다(SKILL.md:65-68).
- `user`의 롤아웃 비용: 0.9.x CLI의 `deliver_messages`는 `message|operator`만 소비한다(bin/khala:2896). 그래서 구 노드로 간
  `user` 메시지는 스풀에 머물다 만료되고, 게이트웨이에 bounce가 돌아간다(§2.2). **B-CLI를 전 노드에 먼저 롤해야 한다**.
  게이트웨이는 `/open` 때 대상 노드의 `.ear` `component conduit release`가 0.10.0 이상인지 확인한다(§4.5). relay와 CLI의
  버전이 다를 수 있으므로 근사 검사다. 롤 순서로 보완한다.

### 2.2 헤더 집합과 순서 (정확히 이 순서, `bin/khala` 한 곳에서만 쓴다)

```
Khala: 0.1
Id: <epoch>.<pid>.<rand>.user@<gw-node>     # new_message_id(bin/khala:1170)와 같은 모양, 주소 부분 = From
From: user@<gw-node>
To: <session>@<node>
Date: <ISO8601 UTC>
Type: user
Origin: telegram                            # telegram | web (web은 예약만, v1은 만들지 않음)
Origin-Ref: <chat_id>/<message_thread_id>/<message_id>   # 게이트웨이만 해석. 음수 chat id 허용: [-0-9]+/[0-9]+/[0-9]+
Subject: <본문 첫 줄 80자, 줄바꿈 제거>        # 선택
Expires: <epoch>                            # 기본 now + 259200(3일), gateway.conf `user expires <초>`, 상한 5097600
<빈 줄>
<Telegram 텍스트 그대로(UTF-8)>
```

- `In-Reply-To`, `Priority`, `Urgency`, `Refs`는 쓰지 않는다. `Priority: later`가 들어 있어도 알림 데몬은 무시한다(§3.1).
- 배달: `message`와 같다. 수신 노드 reconcile이 `inbox/<session>/new/`에 설치하고 ack를 만든다. `deliver_messages`의
  분기(bin/khala:2896)에 `user`를 더해 `deliver_regular_message`(2752-2823, ack 2796)로 보낸다. `copy_outbox_to_spool`의
  "outbox/new에는 message만"(2725-2727)은 `message|user`로 넓힌다. ack가 오면 `settle_acks`가 게이트웨이 노드의
  `outbox/new/<Id>`를 `outbox/acked/`로 옮긴다(2961-). 게이트웨이는 이 이동을 "도착 확인"으로 쓴다(§4.4).
- 만료: 사용자 메시지는 영원히 재전송하지 않는다. `Expires`가 지나면 기존 `expire_outbox`가 bounce를 **한 번** 만들고
  (bin/khala:2929) `outbox/dead`로 옮긴다. bounce는 `user@<gw>` 수신함에 떨어지고, 게이트웨이는 원래 Telegram 메시지에
  답글 한 줄("배달 안 됨: 만료")을 단다. 재발송은 하지 않는다. 사람이 다시 치면 새 메시지가 된다.
- dedup·보존은 message와 같다(`log/delivered` 60일, `cur/` retain).

| `recipient_reserved_name`(162-167) — `send`/`notify`의 To 거부 | 없음 → **오늘도 `send user@mini`가 통과**해 아무도 안 읽는 `inbox/user/new`에 쌓인다 | 그대로 둔다(수신자로 허용). 대신 `send user@<n>`은 `presence/user@<n>`이 없거나 1일보다 오래됐으면 stderr에 경고 한 줄을 내고, 발신은 그대로 한다(§5.2의 내구 큐잉) |
| Go `isReservedIdentity`(link/config.go:127-129) → `runtime register/bind` 거부(link/runtime.go:665, 741) | 없음 | `user` 추가 |
| 채널 `RESERVED_IDENTITIES`(plugin/channel/server.ts:12) | 없음 | `user` 추가 |
| 대시보드 `skipFleetIdentity`(link/dashboard.go:511-513) | 없음 | `user` 추가 |
| `watcher declare --owner`의 예외(bin/khala:4772-4776, 지금은 `khala-gateway`만 허용) | — | `user`도 허용(워치독이 사용자에게 직접 알릴 owner) |

- 현재 클러스터 presence에는 `user@*`가 없다(b200 복제본 `~/.khala/presence` 54개 heartbeat 파일 실측, 2026-09-22). 이미 `user`라는
  이름으로 도는 세션은 없다.
- `khala-gateway`의 거취: DESIGN §3.4는 이 이름을 "B의 회신 주소"로 두었다(DESIGN.md:765, 773-774). 이 설계는 회신 주소를
  `user@<gw>` 하나로 모은다. 게이트웨이가 수신함 두 개를 비우는 일을 없애기 위해서다. `khala-gateway`는 0.10.0에서
  `recipient_reserved_name`에 넣고, DESIGN 표를 "수신 불가, 획득 불가(예약만)"로 고친다. 이 이름을 owner로 선언한 워치독은
  클러스터에 없다고 가정한다. B-CLI의 첫 RED 단계에서 `grep khala-gateway presence/*.watcher`로 확인한다.

### 2.4 게이트웨이가 헤더를 만드는 방법 — 공개 플래그 없이

두 안을 비교했다.

- (가) 게이트웨이(Go)가 `outbox/new`에 헤더를 직접 쓴다. Id·Date·Expires 생성, outbox→spool 물질화, 요청 원장,
  `brain.lock.d` mkdir 잠금 규약(bin/khala:660-)을 Go로 한 벌 더 구현해야 한다. 헤더를 쓰는 곳이 둘이 되고, bash 쪽
  `copy_outbox_to_spool` 검사를 어차피 고쳐야 한다. 테스트 표면이 두 배가 된다.
- (나) **토큰으로 막은 내부 하위 명령**. `bin/khala`에 사용법에 나오지 않는 `khala gateway-enqueue`를 둔다. 조건은 셋이다.
  ① 환경변수 `KHALA_GATEWAY_TOKEN`이 `$KHALA_HOME/run/gateway.token`과 바이트 단위로 같다. 이 파일은 게이트웨이가 기동할 때
  32바이트 난수 hex로 0600, tmp+rename으로 쓰고, 종료할 때 지운다. 파일이 일반 파일·0600·같은 uid인지도 검사한다.
  ② `$KHALA_HOME/gateway.conf`가 존재한다. 즉 게이트웨이 노드에서만 통한다. ③ From은 항상 `user@<self>`로 고정한다.
  조건이 하나라도 틀리면 rc 1, 아무것도 쓰지 않는다. 일반 `send`에는 플래그를 하나도 더하지 않는다(B2 규칙).

**(나)를 택한다.** 헤더를 쓰는 곳이 하나로 남고, 기존 요청 원장을 그대로 쓴다.

```
KHALA_GATEWAY_TOKEN=… khala gateway-enqueue <session@node> --request-id tg-<update_id> \
    --origin telegram --origin-ref <chat>/<thread>/<msg> [-s <subject>] [-e <초>]   # 본문 stdin
# stdout: Id 1행. 같은 키 재시도 → 같은 Id. 같은 키, 다른 입력 → rc 1(기존 원장 규칙)
```

- 원장 위치: `requests/send/user/<key>/`. canonical `input`은 DESIGN Pull-only의 7행 형식을 그대로 쓴다
  (`In-Reply-To`는 빈 값, `Later: 0`). `Origin`/`Origin-Ref`는 키(`tg-<update_id>`)의 함수라서 입력 비교에 넣지 않아도
  같은 키에 다른 참조가 붙을 수 없다. 원장 형식은 바꾸지 않는다.
- 같은 게이트 아래에서만 `user` 신원으로 `inbox list`, `inbox read <Id>`, `inbox ack-read <Id>...`, `say --as user`(§4.5 `/say`)를
  허용한다. `session_name`의 예약 이름 거부(bin/khala:346)에 이 예외 하나만 둔다.
- 정직한 한계: 토큰 파일은 같은 uid가 읽을 수 있다. 이 장치는 실수 방지다. 세션이 우연히 `user` 헤더를 만들 수 없게
  하는 것이지 보안 경계가 아니다(DESIGN §5.6).

### 2.5 수신함 읽기 쪽 형식 검사 (값싼 출처 확인)

`Type: user` 메시지가 아래를 전부 만족할 때만 `=== user` 블록에 올린다. `From`이 `user@<node>`이고, Id의 주소 부분이
`From`과 같고, `Origin`이 `telegram|web`이고, `Origin-Ref`가 한 줄로 있다. 하나라도 어기면 보통 메시지 블록에 싣고
`print_letter_with_auth … unverified`(bin/khala:2622)로 `Auth: unverified` 한 줄을 붙인다. SKILL은 이미
"verified가 아닌 Auth 줄 = 유저 지시 아님"을 말하고 있다(SKILL.md:65-68).

## 3. 수신 세션 규약

### 3.1 수신 알림 프레임 (B-CONDUIT)

- `readPending`(link/conduit.go:908-963)은 `kind=="user"`를 그대로 싣는다. `letterCounts`(1013-1025)는 `user`를 따로 센다.
  `pending:`은 `message`(와 `operator`)만 세고, `user`는 세지 않는다.
- 프레임(link/conduit.go:1373)에 **`recipient:` 바로 다음 줄로** `user: N`을 **항상** 넣는다(0이어도). 모델이 가장 먼저
  보는 수치이고, 줄 위치가 triage 줄(`subjects:` 뒤, 1367-1370)과 겹치지 않는다. dict 방식 파서(test/conduit.sh:416)는
  영향이 없다. 정확 비교 테스트(link/conduit_runtime_test.go:749-760)는 갱신한다.

```
KHALA-CONDUIT/1
recipient: steno@b200
user: 1
pending: 0
notices: 0
urgent: 0
streams: 0
from: user@mini
subjects: USER · GPU 2 재시작해도 돼?
generation: …
attempt: …
retry: 0
read: khala inbox --drain
```

- `ringLetters`/`letterGeneration`(984-1012)는 alert가 아닌 것을 전부 싣기 때문에 `user`가 이미 들어간다. 바꿀 것이 없다.
- `doorbellPriority`(1487-1498): 알림 대상 집합에 `kind=="user"`가 하나라도 있으면 `"next"`를 돌려준다. 헤더의 `Priority`는 보지 않는다.
- `doorbellDisplay`(1388-): user 메시지 제목 앞에 `USER · `를 붙인다. `channelRequest`(1413-): meta에 `user_pending: "<N>"`를 더하고
  content 줄은 `user@mini · USER · <subject>`로 쓴다. **기존 meta 키 `user`(1426-1430)는 발신자 표시용이라 뜻을 바꾸지 않는다.**
- `.ear`: `pending-operator` 값에 `user`(와 `operator`) 대기 수를 채운다. 지금은 항상 0이다(link/ears.go:811-841, DESIGN.md:661).
  `pending-ring`은 계속 user를 포함한다. 새 키 `oldest-operator=<epoch|0>`(그 대기 중 가장 오래된 inbox/new mtime)을 더한다.
  0.9.x 독자는 모르는 키를 무시한다(DESIGN.md:641; Go 파서는 키 맵만 쓰고 bash는 `case`에 기본 분기가 없다,
  bin/khala `read_ear_snapshot`, `ears_test.go:17`의 `future=value`). 값 문법 `[A-Za-z0-9._:+-]{1,64}`를 지킨다.

### 3.2 수신함 읽기 출력 (B-CLI)

`cmd_inbox` 수신함 읽기(bin/khala:5709-6117)의 현재 순서는 메시지(5901-5947, alert 제외 루프) → `N건 더`(5954) → alerts
(5966-6015) → streams(6021-) → 마커(6095-6106) → `drained:` 줄(6115)이다. 여기에 user 블록을 **맨 앞**에 둔다.

```
=== user (2) ===
--- user <Id> --- telegram · user@mini
<파일 전체 그대로: 헤더 블록 + 빈 줄 + 본문>

--- user <Id> --- telegram · user@mini
…
사용자 편지 N건 더                      # 상한 초과 시
--- letter <Id> ---                     # 이하 기존과 같다
…
=== notices (k) ===
…
drained: user 2, letters L, notices N, streams S
```

- 상한은 따로 둔다: `--max-user N`(기본 20), `--max-user-bytes B`(기본 65536). 메시지나 알림이 사용자 메시지를 밀어내지 않는다.
- `--mail-only`는 user를 포함하고, `--notices-only`는 제외한다.
- 요약 줄: **user가 0이면 지금과 바이트까지 같은** `drained: letters L, notices N, streams S`를 찍는다. 1 이상일 때만
  `drained: user U, letters …`를 찍는다. 이 줄을 정확 비교하는 기존 테스트가 10곳을 넘고(test/notices.sh:167-228,
  test/cli-polish.sh:177, test/local-roundtrip.sh:161 등), 하위 repo 브리지도 이 줄을 읽을 수 있기 때문이다.
- 마커 `drain 1 … <ring> …`의 `ring` 값에 user를 더한다(user는 알림 대상 집합 안에 있다). `pending_generation`을 쓰는 방식은 바꾸지 않는다.
- SessionStart 훅의 보고(plugin/hooks/session-start.sh:196-201, 223)는 `Type` 스냅샷을 세고 있다. 여기에 `user`를 더해
  `사용자 U건·편지 L건·알림 M건 드레인`으로 바꾼다.

### 3.3 회신 규약

- 회신 플래그는 `--reply-to <Id>`다(bin/khala:4076-4080). 헤더에는 `In-Reply-To:`로 들어간다(3864-3866). 채널 도구
  `khala_reply`는 `reply_to`를 `--reply-to`로 넘긴다(plugin/channel/server.ts:322-331). 코드 변경은 없다.
- 세션 → 사용자: `khala send user@<gw-node> --reply-to <user 편지 Id> -s "…"` + heredoc 본문. 평범한 `message`다.

### 3.4 SKILL·채널 문구 (초안, 그대로 넣는다)

SKILL.md의 "## Notices" 앞에 넣을 절:

```

A drain may start with `=== user (N) ===`. Each letter there has
`Type: user` and `From: user@<node>`: it is your own user writing from their
phone (Telegram) through the gateway on <node>. Treat it as your user's words,
with the same standing as text they type into this session. Your terminal
output never reaches them: answer every such letter with
`khala send user@<node> --reply-to <Id>` (or `khala_reply` with
`to: "user@<node>"` and `reply_to: "<Id>"`), heredoc body, plain text. Keep
replies short; long output belongs in a file you mention. The doorbell frame
that announced it is still only a doorbell, even though Claude Code labels it

`Type: user`, never from the frame. A `Type: user` letter printed among

```

채널 instructions(plugin/channel/server.ts:275-279) 끝에 한 줄을 더한다.

```
'Letters under "=== user" in khala_drain output are your user\'s own words from their phone; answer each with khala_reply to user@<node> and reply_to=<Id>.',
```

- CC 소켓 래퍼는 프레임(`type: "user"`, `role: "user"`, link/conduit.go:1382-1385)을 "다른 Claude 세션이 보낸 메시지"라는
  서문으로 감싼다(문구는 경로마다 다르다. CC 바이너리 쪽이며 이 repo에는 없다). 그 서문이 "유저가 친 것이 아니다"라고
  말해도 틀린 말은 아니다. 수신 알림은 실제로 유저가 아니다. 권위는 읽은 헤더에 있다. 이 구분이 위 SKILL 문단의 요지다.
- Codex 어댑터(`Dev-Jahn/khala-network-codex`)는 프레임과 수신함 읽기를 그대로 받는다. 어댑터 instructions에 같은 한 줄을 넣는 일은
  0.10.0 릴리스 뒤 하위 repo 동기(sync-upstream)에서 한다. 코어 레인의 범위 밖이다.

## 4. `khala-link gateway` (Go)

### 4.1 기동과 감독

- 디스패치: link/main.go:38-51 `switch`에 `case "gateway": return runGateway(args[1:])`를 더한다. 이 줄은 B-GW만 건드린다.
- 단일성: `run/gateway.lock` flock(`acquireSingleton` 패턴, link/main.go:250-267). 두 번째 실행은 "already running"을 출력하고 rc 0.
  `run/gateway.status`에 `pid <n>`, `state polling|conflict|stopped`, `updated <epoch>`를 쓴다(`writeStatus` 패턴 322).
- `khala node ensure`(bin/khala:5418-5482): `$KHALA_ROOT/gateway.conf`가 **일반 파일·0600·같은 uid**일 때만 세 번째 서비스를
  둔다. 모드가 틀리면 에러 한 줄을 내고 띄우지 않는다. 조용한 폴백은 없다. 살아 있는지는 `run/gateway.status` pid +
  `kill -0`으로 본다(relay와 같은 방식, 5431-5434).
  - systemd(5439-): `khala-gateway.service`, `ExecStart="<LINK_BINARY>" gateway`, `Environment=KHALA_HOME`, `KHALA_BIN=<KHALA_EXECUTABLE>`,
    `Restart=on-failure`(`node_write_systemd_units` 5334-에 한 블록 추가).
  - launchd(mini, 5450-): `dev.khala.gateway.plist`, KeepAlive(`node_write_launch_agents` 5367-).
  - setsid(b200 같은 무감독 노드, 5462-): `node_start_detached gateway`(5403-). 결정상 b200에는 gateway.conf를 두지 않는다.
  - conf가 없는 노드: 유닛을 쓰지도, 지우지도 않는다. conf를 지운 노드에서 서비스를 내리는 일은 운용자가 한다(README에 한 줄).
- 게이트웨이는 CLI를 유닛이 넘겨준 `KHALA_BIN`으로 부른다. 없으면 PATH의 `khala`를 쓰고, 그것도 없으면 기동하지 않는다.
  모든 CLI 호출에 `KHALA_GATEWAY_TOKEN`을 싣는다.

### 4.2 설정·상태 파일

`~/.khala/gateway.conf`(0600, 한 줄 = 한 사실. 모르는 키나 중복 키는 기동 실패. triage.conf 파서와 같은 엄격성):

```
telegram token 123456:ABC…            # 또는: telegram token-file /abs/path (0600)
telegram chat -1001234567890           # 포럼 슈퍼그룹 숫자 id
telegram allow 11111111 22222222       # 숫자 user id만. username은 받지 않는다
notices forward off                    # off | urgent | all (기본 off; 토픽별 /notices가 덮는다)
user expires 259200                    # 선택, 1..5097600
```

`~/.khala/gateway.state`(0600, 게이트웨이 단독 쓰기, tmp+rename, 줄 단위, grep으로 읽힌다):

```
state 1
offset <마지막으로 enqueue를 끝낸 update_id>
topic <thread_id> <session@node> open|closed
notices <session@node> off|urgent|all
status <session@node> listening|stuck|asleep <since-epoch> <generation|->   # 마지막으로 게시한 상태(중복 게시 방지)
posted <letter-Id> <telegram message_id>[,<id>…]                             # 게시 완료, ack-read 전후 복구용
```

- 매핑은 숫자 `message_thread_id`로 한다. 토픽 이름(=주소)은 표시일 뿐이다. 상태 파일을 잃으면 매핑은 `forum_topic_created`
  서비스 메시지로만 복구할 수 있는데, getUpdates는 24시간 안의 것만 준다(실측 항목). 그래서 상태 파일은 백업 대상이다(README).
- `posted` 줄은 ack-read가 끝나면 지운다. 크기를 제한한다.

### 4.3 어댑터 인터페이스와 Telegram 어댑터

```go
type inboundEvent struct {
    UpdateID   int64
    ChatID     int64; ThreadID int; MessageID int; FromUserID int64
    Text       string
    TopicCreated *struct{ Name string } // forum_topic_created
}
type adapter interface {
    // Poll blocks for at most ~30 s; returns events after offset. Commit is separate.
    Poll(ctx context.Context, offset int64) ([]inboundEvent, error)
    Post(ctx context.Context, thread int, text string, replyTo int) ([]int, error) // chunked message ids
    CreateTopic(ctx context.Context, name string) (int, error)
    SetTopicState(ctx context.Context, thread int, open bool) error
    React(ctx context.Context, thread, message int) error // 도착 확인 표시; 실패해도 무시(로그 1줄)
}
```

브리프의 `inbound(text, originRef)` / `outbound(topic, text)`를 풀어 쓴 것이다. 코어 쪽 게이트웨이 로직(매핑, 메시지 만들기,
상태 판정, 큐)은 어댑터를 모른다.

**Telegram 어댑터 = stdlib `net/http` + `encoding/json`.** 부르는 메서드는 `getMe`, `getUpdates`, `sendMessage`,
`createForumTopic`, `closeForumTopic`, `reopenForumTopic`, `setMessageReaction`, `getChat` 여덟 개다.
- `go-telegram/bot` v1.27.0은 proxy에서 받아지고(모듈 캐시 실측, go.mod `go 1.18`, 순수 Go, README 기준 Bot API 10.3 지원)
  `CGO_ENABLED=0` 4종 자산에 얹을 수 있다. 그런데 폴링 루프가 업데이트를 채널로 넘기기 **전에** `lastUpdateID`를 전진시키고
  (`get_updates.go:95` → `:106`), 다음 `getUpdates` 요청이 그 offset을 확인해 버린다. 핸들러는 워커에서 비동기로 돈다.
  그래서 enqueue가 끝나기 전에 Telegram 쪽 확인이 날 수 있고, 그 순간 죽으면 사람 메시지가 사라진다. 공개 `GetUpdates`도
  없다(`getUpdates`는 비공개, get_updates.go:28). 이 라이브러리로 "enqueue 뒤 확인"을 하려면 결국 폴링을 직접 짜야 한다.
  따라서 의존성을 늘리지 않는다. link/go.mod는 지금처럼 `fsnotify` 하나로 둔다.
- 수신 순서(유실 없음): `getUpdates(offset=state.offset+1, timeout=25, allowed_updates=["message"])` → 업데이트마다
  ① chat id가 conf와 다르거나 from id가 allow 목록에 없으면 버리고 식별자당 한 번만 로그 → ② 명령/토픽 글 처리(§4.5),
  토픽 글이면 `gateway-enqueue --request-id tg-<update_id>` → ③ 성공한 뒤에만 `offset` 기록. 중간에 죽어도 Telegram이 다시
  주고(확인 안 된 업데이트는 최대 24시간 보관), 원장이 같은 Id를 돌려준다. 24시간 넘게 꺼져 있으면 잃는다는 점은 문서에 적는다.
- 409 Conflict(다른 getUpdates 소비자나 웹훅이 있음): `state conflict`로 쓰고, 60 s에서 10 min까지 지수 백오프한다.
  종료하지 않는다(launchd KeepAlive 재시작 폭주 방지). `deleteWebhook`을 저절로 부르지 않는다. `khala status`가
  `gateway: conflict`를 보인다(B-CLI가 status에 한 줄 추가).
- 발신 큐: chat 하나에 큐 하나. 토큰 버킷은 **분당 20건, 초당 1건**(Bots FAQ: 그룹에서 분당 20건 초과 불가, 채팅당 초당 1건
  권고). 우선순위는 명령 응답 > 상태 게시 > 세션 회신 순이고, 토픽 사이는 라운드로빈이다. 같은 토픽에 밀린 회신은
  합쳐서 4096자를 넘지 않을 때만 하나로 묶는다. 429는 `retry_after`를 따른다.
- 청킹: 텍스트는 파싱 모드 없는 평문으로 보낸다(엔티티 오프셋 문제 제거). 한도 4096자를 **UTF-16 코드 단위 4000**으로
  보수적으로 잡고, 줄바꿈 → 공백 → 룬 경계 순으로 자른다. 조각이 여럿이면 앞에 `(i/n) `을 붙인다. 원 메시지의 In-Reply-To
  답글 지정은 첫 조각에만 한다. Telegram이 글자를 세는 단위가 UTF-16인지는 실측 항목이다.

### 4.4 사용자 수신함 비우기 (게이트웨이만)

- `inbox/user/new`를 fsnotify로 감시하고(백업으로 30 s 주기) `gateway-enqueue`와 같은 토큰으로 `khala inbox list` →
  `inbox read <Id>`를 부른다. 파괴적 `--drain`은 쓰지 않는다.
- 메시지 종류별 처리:
  - `message`(세션 회신): `From`의 토픽을 찾는다. 없으면 `createForumTopic(name=From)`로 만들고 매핑을 저장한다. `closed`면
    `reopenForumTopic`. `In-Reply-To`가 게이트웨이가 보낸 user 메시지 Id를 가리키면 **자기 노드**의 `outbox/{new,acked,dead}/<Id>`에서
    `Origin-Ref`를 읽어 그 message_id에 답글로 단다. 본문 앞에는 `Subject`가 있을 때만 `[subject]` 한 줄을 붙인다.
  - `bounce`(`Refs` = user 메시지 Id): 원래 Telegram 메시지에 "배달 안 됨: <To> — 만료" 답글. 상태 게시와는 다른 범주다
    (사람이 한 행동에 대한 결과다).
  - `notice`(워치독이 `notify user@<gw>`로 보냄): §4.7.
  - 그 밖(`operator` 등): 게시하지 않고 로그 한 줄 + ack-read.
- 게시가 성공하면 `posted` 기록 → `inbox ack-read <Id>` → `posted` 줄 삭제. 게시 뒤·기록 전에 죽으면 한 번 더 게시될 수 있다
  (at-least-once. 문서화된 절충이다).
- 도착 확인: 게이트웨이가 만든 user 메시지의 Id가 `outbox/acked/`로 옮겨지면(자기 노드 파일, fsnotify) 원 Telegram 메시지에
  반응 하나를 단다. 게시가 아니라 반응이다. 쓸 수 있는 이모지 집합은 실측 항목이다. 실패는 무시한다.

### 4.5 General 토픽 명령 (자연어 처리 없음)

| 명령 | 동작 |
|---|---|
| `/sessions` | 복제된 `presence/*` 세션 행 + 각 노드 `.ear`의 `listening`·`pending-operator`를 한 화면 요약(≤4000자). 원격 runtime dir은 읽지 않는다 |
| `/open <session@node>` | 주소 검증 → 대상 노드 `.ear`가 fresh이고 `component conduit release` ≥ 0.10.0인지 확인. 아니면 거절하고 이유 한 줄. 이미 매핑돼 있으면 그 토픽을 알려 준다. 없으면 `createForumTopic` 후 저장 |
| `/close` (토픽 안에서) | `closeForumTopic` + `closed`. 그 세션이 다시 메시지를 보내면 reopen |
| `/say <stream> <text>` | `khala say <stream> --as user`(토큰 게이트). 이 경로만 스트림 엔트리 `From: user@<gw>`를 만든다 |
| `/notices <session@node> off\|urgent\|all` | 토픽별 alert 전달 정책을 바꾼다 |

- General에서 `/`로 시작하지 않는 글은 무시한다. 매핑되지 않은 토픽의 글은 "`/open`으로 먼저 연결하세요" 한 줄로 답한다.
- General 토픽의 스레드 id가 업데이트에 어떻게 실리는지(없음 또는 1)는 실측 항목이다. 판정은 "매핑된 thread id인가"로만 한다.

### 4.6 자동 상태 게시 — 정확히 세 종류

입력은 **자기 노드에 복제된 `presence/conduit@<node>.ear`뿐**이다. 파서는 `parseEars`를 재사용한다(link/ears.go:103).
신선도는 DESIGN 3.2 규칙(`−60 ≤ now−written-at ≤ 2×interval+60`)을 따른다. 매핑된 토픽의 주소에 대해서만 30 s마다 평가한다.

| 게시 | 조건 (identity 레코드 `name=<session>`) | 문구 |
|---|---|---|
| 듣는 중 | 스냅샷 fresh ∧ `listening=yes`. 직전 게시 상태가 없거나 `asleep` | `듣는 중 (<route>, cc=<cc>)` |
| 수신 가능하나 미처리 | fresh ∧ `listening=yes` ∧ `pending-operator>0` ∧ (`written-at − oldest-operator`) + 스냅샷 나이 ≥ 15분. **같은 `generation`에 한 번**만 | `초인종은 닿았으나 사용자 편지가 <m>분째 드레인되지 않음 (초인종 <written-rings>회)` — 원인(한도·권한 대기)은 단정하지 않는다(GPT-Pro B6) |
| 잠듦 | 직전 상태가 `listening`/`stuck`이고, 연속 두 번의 평가(≥60 s)에서 레코드가 `listening=no`이거나, 스냅샷이 stale | `잠듦 — 편지는 보관되고 깨어나면 전달됨` |

- `state stopping` 스냅샷(재시작 과도 상태)과 `complete no`에서 레코드가 빠진 경우(= unknown)는 어느 전이도 일으키지 않는다(DESIGN 3.1).
- 이 셋 말고는 게이트웨이가 스스로 게시하지 않는다(명령 응답, 세션 회신, bounce 답글, opt-in alert는 사람이나 세션의 행동에서 나온다).

### 4.7 alert 전달 (기본 off)

- 다른 노드 세션 앞으로 온 alert는 게이트웨이가 볼 수 없다. 원격 inbox는 복제되지 않는다. 이것이 맞는 동작이다. 사용자에게
  알릴 일은 세션이 정리해서 보낸다.
- 워치독이 `notify user@<gw>`로 직접 보낸 alert만 대상이다. 게시할 토픽은 그 워치독 `.watcher` 마커 L3의 owner 토픽이다
  (마커는 복제된다, DESIGN §9.6 watchdog marker). owner가 `user@…`이거나 토픽이 없으면 General이다. 정책은 토픽별 `/notices`,
  그다음 conf 기본값(`off`) 순서다. `urgent`면 urgent만 `⚠ <watcher> · <subject>` 한 줄로 요약한다. 본문은 싣지 않는다.
  게시하지 않은 alert도 ack-read로 치운다.

### 4.8 대시보드는 분리한 채로 둔다

`khala-link dashboard`는 필요할 때만 띄우는 루프백 전용 읽기 서버다. 토큰을 실행마다 새로 만들고 GET/HEAD만 받는다
(link/dashboard.go:216-229, 256-258). 게이트웨이는 봇 토큰을 들고 쓰기 경로(enqueue)를 가진 상주 프로세스이고, 한 노드에만 있다.
둘을 합치면 비밀과 쓰기 경로 옆에 HTTP 리스너가 붙고, 대시보드가 gateway.conf가 있는 노드에서만 도는 제약까지 생긴다. 합쳐서
얻는 이득은 없다. 대시보드의 "user 보내기"(`Origin: web`)는 v1 비목표로 둔다. v1이 바꾸는 것은 대시보드의 `skipFleetIdentity`에
`user`를 더하는 것 하나다(B-CONDUIT). 대시보드의 메시지 표는 이미 `Type`/`Origin` 열을 가지고 있다(dashboardLetter, dashboard.go:128-142).

충돌 지점과 해결:
- `DESIGN.md`/`README.md`: **B-CLI만** 고친다. B-CONDUIT과 B-GW는 문서 문안을 `report/d17-b-<lane>.md`에 남기고, main이 병합할 때
  B-CLI 편집 위에 옮긴다.
- 프레임 줄(`link/conduit.go:1373`)과 triage 줄의 위치는 **B-CONDUIT만** 다룬다. `link/triage.go`는 어느 레인도 건드리지 않는다.
- `link/main.go`는 B-GW만 건드린다. 버전 상수 `linkVersion`(main.go:24)과 채널 `version`(server.ts:272)은 릴리스 커밋에서만 바꾼다.
- `plugin/channel/server.ts`의 예약 집합과 instructions는 B-CLI만 고친다. meta 키 `user_pending`은 알림 데몬이 만들고 채널 자식은
  그대로 넘기므로(VALID_META_KEY 통과) 서버 코드를 바꿀 필요가 없다.
- `isReservedIdentity`(Go)와 `reserved_name`(bash)은 레인이 다르다. 같은 이름 집합이라는 불변식은 양쪽 RED 테스트가 각자 증명한다.

사전 등록 수용 속성(각 레인은 RED부터 커밋한다):

B-CLI
- C1 `user`는 `KHALA_SESSION`·`.khala-session`·`--as`·`watcher declare`·`notify --as`에서 `예약된 이름입니다: user`, rc 1.
- C2 세션의 `khala send user@alpha -m hi`는 성공한다(`Type: message`). `presence/user@alpha`가 없으면 stderr 경고 1줄, stdout은 Id만.
- C3 `gateway-enqueue`: 토큰 없음·불일치·gateway.conf 없음·토큰 파일 0644일 때 각각 rc 1이고 파일을 만들지 않는다. 정상이면 §2.2 헤더를
  순서까지 정확히 쓴다. 같은 키 재시도는 같은 Id, 같은 키에 다른 본문은 rc 1.
- C4 reconcile이 `user`를 `inbox/<s>/new`에 넣고 ack를 만든다. 게이트웨이 노드는 `outbox/acked/<Id>`.
- C5 수신함 읽기 순서 `=== user` → messages → alerts → streams. user 상한이 따로 적용된다. `--notices-only`는 user를 빼고,
  user 0이면 `drained:` 줄이 바이트 동일하다. 마커의 `ring` 값에 user가 포함된다.
- C6 형식 검사에 실패한 `Type: user`(From 불일치 등)는 messages 블록에 `Auth: unverified`와 함께 나온다.
- C7 만료된 user 메시지는 bounce를 정확히 1회 만든다 → `outbox/dead`. 이후 pass에서 재생성은 0.
- C8 `node ensure`: conf가 없으면 gateway 유닛을 만들지 않는다. 0644면 에러 1줄을 내고 띄우지 않는다. 0600이면 유닛을 쓰고 기동한다(systemd·setsid 경로를 테스트, launchd는 유닛 파일 내용 비교).
- C9 기존 스위트(local-roundtrip, alerts, cli-polish, streams, watchdogs, triage, plugin) 무변경 PASS. `cmp bin/khala plugin/bin/khala`.
- C10 SessionStart 보고에 `사용자 U건`.

B-CONDUIT
- K1 프레임 2행이 `user: N`이고 `pending:`에서 user는 빠진다(정확 비교). user가 0이어도 줄은 있다.
- K2 알림 대상 집합 전부가 `Priority: later`여도 user가 하나 있으면 `priority=next`. user 메시지 자신의 `Priority: later`도 무시한다.
- K3 채널 meta `user_pending`, content 줄 `… · USER · …`. 기존 meta `user`(발신자 표시)는 불변.
- K4 `.ear`의 `pending-operator`가 user 수를 담는다. `oldest-operator` 키. 0.9.9 bash `read_ear_snapshot`과 Go `parseEarsBytes`가 새 파일을 받는다.
- K5 `runtime register --identity user`는 거부된다. 대시보드는 `user` 행을 건너뛴다.
- K6 triage는 user 메시지에 태그를 만들지 않는다(기존 kind 검사 회귀 테스트).

B-GW
- G1 매핑된 토픽 글 1건 → `gateway-enqueue` 1회(`tg-<update_id>`). 같은 update를 다시 넣으면 같은 Id이고 메시지는 1통.
- G2 enqueue가 실패하면 offset이 전진하지 않아 다음 Poll에서 다시 처리된다.
- G3 allow 밖 user id나 다른 chat id → 메시지 0, 로그는 식별자당 1줄.
- G4 `/open`은 토픽 생성과 state 저장을 하고 재기동 뒤에도 매핑이 유지된다. `.ear`가 없거나 stale이거나 release < 0.10.0이면 거절 문구.
- G5 회신은 From 토픽으로 가고, `In-Reply-To`가 user 메시지면 원 message_id에 답글. 게시 → `posted` → ack-read 순서. ack-read 전에 죽으면 재기동 때 최대 1회 재게시.
- G6 토픽이 없는 발신자 → 토픽 생성 후 게시. `closed` → reopen.
- G7 50건을 큐에 넣으면 어느 60 s 창에서도 ≤20건, 초당 ≤1건. 명령 응답이 먼저 나간다. 429 `retry_after` 준수.
- G8 10,000자 → 조각 3개, 각 ≤4000 UTF-16 단위, 서로게이트 쌍이 깨지지 않고, `(i/n)` 순서가 맞다.
- G9 합성 `.ear` 시퀀스에서 게시가 정확히 3종이고 전이마다 1회다. `stopping`과 `complete no`로 빠진 레코드에는 게시 0. 미처리는 같은 queue digest에 1회.
- G10 alert: 기본 off면 게시 0. 토픽 `/notices urgent` + urgent alert면 요약 1줄. info는 0.
- G11 409면 `state conflict`, 백오프하고 프로세스는 유지된다. 같은 노드의 두 번째 기동은 flock으로 rc 0 "already running".
- G12 `CGO_ENABLED=0 go build` 4종(linux/darwin × amd64/arm64) 성공. `go.mod`의 require는 불변(`fsnotify`만).
- G13 user 메시지 bounce → 원 메시지에 "배달 안 됨" 답글 1개.

## 7. 비목표 (v1)

- 폰에서 권한 프롬프트를 승인하는 permission relay. 클러스터는 skip-permissions로 돈다.
- 봇의 자연어 처리와 라우팅 추론. 명령은 `/` 접두만 받는다. 매핑은 토픽으로만 한다.
- 자체 앱이나 Web Push. 대시보드의 `Origin: web` 보내기.
- 워치독 alert 전체 전달. 원격 세션 앞 alert 관찰.
- 첨부나 이미지(텍스트만 받는다. 첨부가 온 업데이트는 "텍스트만 지원" 한 줄로 답한다).
- 게이트웨이 이중화나 페일오버(노드 하나, 토큰 하나).
- `Type: operator` 서명 레인(열린 결정 1이 `user`로 가면 v2에서 다룬다).

## 8. 실측 항목 (추측으로 적지 않은 것)

1. 포럼 슈퍼그룹 General 토픽 글의 `message_thread_id` 표기(없음/1).
2. 관리자 봇이 privacy mode와 상관없이 토픽의 모든 글을 받는지.
3. `sendMessage` 4096 한도를 세는 단위(UTF-16 코드 단위 가정).
4. `setMessageReaction`에 쓸 수 있는 이모지 집합, 봇이 그룹에서 반응을 달 수 있는지.
5. 토픽 수 상한(문서에 없음. 60개까지 생성 시험).
6. 분당 20건이 토픽마다가 아니라 그룹 전체에 걸리는지(FAQ 문언은 그룹 기준).
7. CC 2.1.26x에서 공식 마켓 밖 채널 게이트가 여전한지(§1 표 8행).
8. 24시간 넘게 멈췄을 때 사라지는 업데이트의 실제 범위.

## 9. 열린 결정 (유저 몫)

1. **헤더 이름**: 이 문서대로 서명 없는 `Type: user`로 간다(롤 순서 필수, 위조 한계는 §5.6 안), 아니면 이미 예약된 `Type: operator` +
   Ed25519 서명으로 간다(구 노드도 배달하지만 서명 구현이 필요하다). 권고: v1은 `user`, 서명은 필요가 생기면.
2. **`khala-gateway` 이름 정리**: 회신 주소를 `user@mini` 하나로 모으고 `khala-gateway`를 수신 불가로 바꾼다(DESIGN §3.4 개정). 이견이 없으면 그대로 간다.
3. **사용자 메시지 기본 만료** 3일(메시지가 만료되면 폰에 "배달 안 됨"이 뜬다). 더 길게(예: 7일) 할지.
4. **"미처리" 경보 문턱** 15분(GPT-Pro 권고값). 더 짧게 할지.
